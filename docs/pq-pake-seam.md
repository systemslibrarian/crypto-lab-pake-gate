# The PQ-PAKE seam: KEM ≠ group

A password-authenticated key exchange like the four in this lab runs a Diffie–Hellman inside a group: both peers derive a password-dependent group element and combine private scalars over it. A key-encapsulation mechanism (KEM) — the shape post-quantum primitives such as ML-KEM take — has **no group structure to run a DH over**; there is no scalar multiplication, no password-derived generator, nothing to "juggle." So a real PQ-PAKE cannot do PAKE *inside* the KEM. Instead, constructions like CAKE/OCAKE and Noise-KEM-PAKE keep the classic EKE idea and move it up a layer: they **encrypt or blind the KEM public key (and/or ciphertext) under a password-derived symmetric key**, then run the KEM normally, so an attacker who cannot guess the password cannot recover a usable public key to encapsulate against. Because the password now keys a *symmetric wrapper around* the KEM rather than a *generator within* a group, the extension seam in `src/pake/types.ts` consumes a `KemBackend` plus a `PasswordKeyedEncoding` (the EKE-style wrapper) — never a `DhGroup`. That type distinction is the seam: a PQ-PAKE engine is wired to `KemBackend + PasswordKeyedEncoding`, and the four current DH-group engines are wired to `DhGroup`, so the two families cannot be accidentally interchanged.

## Status and security model (13 October 2026)

This is an **unimplemented extension interface**, not a PQ-PAKE engine or security proof. The four runnable engines remain classical and are marked `quantumResistant: false`. A post-quantum KEM plus a password-keyed wrapper does not by itself establish post-quantum security for the resulting protocol.

Bartusek and Januzelli’s [*Natural Barriers to Quantum Extraction: On the Post-Quantum (In)security of (O)EKE and Masny-Rindal OT*](https://eprint.iacr.org/2026/2280), revised **9 October 2026**, is a **preprint with attack-model-conditional theoretical results**. It separates classical from quantum universal composability (UC) for EKE/OEKE under quantum access to idealized symmetric primitives, while establishing certain game-based guarantees. Those are different security notions; the result is not a practical break of this lab’s classical engines.

The author’s [12 October 2026 CFRG disclosure](https://mailarchive.ietf.org/arch/msg/cfrg/wCtFcJB8X3IhmA20mYTLyy-TnqU/) states that no concrete OQUAKE attack is currently known. Any future implementation must identify its precise construction, draft/version, adversary access model and claimed security notion, and check the corresponding proof; the interface types alone establish none of those guarantees.
